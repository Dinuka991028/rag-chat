1 INTRODUCTION The purpose of the requirements specification is to establish user requirements for the proposed Portal for Small Vessels Registration accommodating MTT initial business requirement as the base. The required logical processes and data are modelled to establish the business solution. The final development estimates are based on this document. The document is aimed at both the user and system development community. The system will provide the services to MTT’s customers and integrate with stakeholders, providing services to internal and external clients in a way that will help to continue the automation and smart services journey. The proposed application will comprise of the following main components: − Laserfiche software o Internal portal (Administration and workflow related functions) o File repository o Workflow management system − Customer portal − Mobile application − MicroServices for third party integration 1.1 INTENDED AUDIENCES The intended audiences of stakeholders for this specification include the following user groups. Users of MTT and MOI will have multiple roles and can access the system for varied functions of the below categories. − Registrar − Inspector − Supervisor − Director − MOI Officer − MTT Finance − MTT IT Administration

2.2.3 STATUS TRACKER The users shall be able to check the status of the requested services anytime. The Status Tracker enables the Portal user to track the status of the applications he has submitted via the Portal. This screen will consist of an overview of the applications, with the latest application been displayed first. The page will also feature a filter and search facility whereby the Portal user can search by Service name, Vessel names and Date of Request/Submit. Given below is a snapshot of statuses across all processes. In Progress The process request has been submitted by the customer and is currently being reviewed by internal teams at MTT. Make Payment The application has been reviewed and the customer has to now make the required payment to move forward and further process the request. Rejected The request was rejected by the authorized MTT officers. Defected The submitted request has been referred back to the customer for changes or reviews. Inspection Scheduled Inspections required for this service, have been arranged by the respective officers and agreed upon by the portal user.

Inspection On-going The scheduled inspection is currently being conducted. Process Completed The process has successfully completed and is now closed. 2.2.4 MESSAGING TOOL The Messages section will be made up of the following components; - Inbox - Send New Message - Sent Messages - General Contact A notification will be sent to (small-ships@mtt.gov.bh) for messages received via the portal.

Inbox The Inbox will list all messages that the portal user has received from MTT with regard to each service request. Each message will contain the following; - Message ID - Message Subject - Message Date - Status (New / Read) The user can read the message by clicking on the message subject to open. The messages will be ordered according to the latest date. Send New Message By Clicking on the ‘Send New Message’ tab the user would be taken to the contact us form. The date and username will be already captured on the form. The user will enter a message subject and message content and submit the message to the MTT. Message content will be limited to 1000 characters and there will be no restriction in terms of character language – English/Arabic. Sent Messages The Sent Messages section displays the messages sent by the Portal user to the MTT. The message list will be ordered by date in descending order, but the list can be re-sorted by clicking on the listing headings. The user can view the sent message by clicking on the message subject. General Contact The General Contact us section will list the contact details of the MTT.

2.2.5 PAYMENTS The ‘Payments’ section will provide the user with details about their financial transactions relating to each service request. This section would be made up of the following sub sections: - Pending Payments - Transaction History - Tariff Pending Payments This section will display all the pending transactions the user needs to complete payment with MTT. The user can choose to pay one or many transactions at the same time through the online payment gateway. Each transaction would provide details of the, Job ID, Service Name, Vessel/Jet Ski Name, status (Expiring soon, Expired) and the value.

The user can choose to pay for prescribe fee online through the Portal or he can submit the payment manually by visiting the MTT. To pay for the selected transactions, the user has to select the Job ID by clicking on the ‘tick box(s)’ and clicking Continue. Once the user clicks ‘Continue he would be taken to the payment summary page. This includes the date, Transaction Number(s) being settled, Vessel details, Service names and the total amount to be paid for all selected transactions. Once the Portal user clicks on ‘Pay’ to process the payment, the transaction details are submitted to the IGA NPA payment gateway for validation. Based on the validation a successful or unsuccessful message (along with payment gateway error) would be displayed to the user. An email of the transaction receipt will also be sent to the Portal user’s registered email address. Transaction History The transaction history page would allow the Portal user to search for the transactions made via the Portal, i.e. online transactions. The search parameters can be a combination of the following; - Transaction Status (All / Successful / Unsuccessful) - Service Name (All / List of service names) - Vessel Name (Owned by/registered to authorized login user) - Period (From – To) In addition to the search criteria a summary of the last transaction would be made available on the same screen showing: - Date of transaction - Transaction Reference Number - Service Name - Vessel Name - Card Type – Credit/ Debit - Value (BHD) - Status (Success/Failure)

3 FUNCTIONAL WORKFLOW REQUIREMENTS This section of the SRS specifies the functional requirements of the Ship Registry Directorate – Small Vessels Registration Systems in terms of workflow process mapping, input data, wireframe and documentation requirement. 3.1 NEW REGISTRATION FOR PLEASURE AND FISHING VESSELS The main functional service available to a customer, is the ability to register Pleasure Vessels and Fishing Vessels. 1. The service is initiated by the customer, where the registration form is submitted along with the required documents. 2. The registrar will then review the request and return to customer if documents are missing, or information is incorrect. When everything is in order, the registrar would approve the request, forwarding for necessary approvals by the supervisor. 3. The supervisor would then approve/reject the forwarded request. If needed, the request would be sent back to the registrar for further changes. 4. Once the request is approved by the registrar and supervisor, the customer would be requested to pay the registration fee/ inspection fee. 5. The customer will then make the requested payment, which is verified and validated by the System and transaction details will be passed to CFS (Central Finance System) for receipt generation. 6. The online or offline payment is verified, the customer will receive the letter to print the number plates and stickers from a selected printing house. Inspection sub-workflow process 7. The inspector plays the pivotal role within this process. He would schedule the inspection and notify all concerned parties. 8. From that point, when a date is agreed upon, the inspection is conducted. 9. The inspector would proceed to submit a report containing the inspection checklist to the supervisor of the information identified. This can be conducted via the inspection process sub- workflow task screen shown below. The interface would act as a single point for inspector and customer to upload and communicate inspection related details. 10. The supervisor would review the report and take the decision on how to proceed. He would opt- to approve the inspection and move forward or report defects back to the inspector. 11. If there are defects,

11.1. The inspector would notify findings and defects to the customer. 11.2. The customer would take necessary measures and upon rectification, he would submit proof of rectification and the changes done. This can be done via the inspection process sub-workflow task screen shown below. 12. Upon customer rectification and submission, the supervisor will decide on if a re-inspection is needed. If required, 12.1. The customer must pay another inspection fee. 12.2. The customer will then make the requested payment, which is verified and validated by the SSRP system. 12.3. The process flow would then continue from above inspection sub-workflow process (step 7 to 13) 13. Once the inspection is approved, The MOI Officer would update the device number. (If AIS device is not required, MOI Officer will update the field as “Not Applicable”) 14. The registration process is now complete allowing the customer to download registration certificate.
